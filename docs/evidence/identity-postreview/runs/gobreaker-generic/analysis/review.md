## Added findings and evidence

- **N01.** A retained completion follows the wrapper receiver's current underlying breaker but supplies the generation captured at admission. With sequential reassignment to an independent closed breaker in the same generation, a false report reaches the replacement's policy hook with `Requests=0` and one failure. That hook returns true, which opens the replacement and clears its counts. In the control, the replacement has already cycled back to closed and its higher generation causes the false report to reach neither hook. The original admission stays pending in both cases. F22's earlier unequal-generation control used an open target, where a success would have no accounting effect even if it passed the generation check. The new control keeps the target closed, where it could count and trip on a matching false report. [Callback capture and lookup](../gobreaker.go#L265) · [Reporting order](../gobreaker.go#L293) · [Outcome branches](../gobreaker.go#L310) · [New probes](./_postprobe/identity_test.go)
- **N02.** With intervals disabled, the two fresh breakers reach generation 1 on construction, generation 2 on opening and generation 3 on entering half-open. Each admits one trial. After sequential reassignment, the original completion's success closes the target and clears its counts. The target's own pending failure is then stale. The original remains half-open with its trial pending until the wrapper is restored, after which the same callback closes the original too. The probe uses wrapper copies that alias the original breaker, and writes and callback calls are sequential. [Initialization](../gobreaker.go#L141) · [Wrapper and callback](../gobreaker.go#L136) · [Half-open success](../gobreaker.go#L310) · [Generation increment](../gobreaker.go#L363) · [New probes](./_postprobe/identity_test.go)
- **N03.** The first `State` call after open expiry commits half-open before the notification panics. It propagates the panic and returns no state. A retry returns half-open with no replay, and a fresh trial can close the breaker. The preceding `Counts` call does not trigger the notification. This establishes the behavior behind the baseline's observation question, which remains open as an API contract question. [State and Counts](../gobreaker.go#L205) · [Transition and notification](../gobreaker.go#L334) · [New probes](./_postprobe/identity_test.go)
- **N04.** `runtime.Goexit` from `ReadyToTrip` terminates the worker after the failure increment and before a trip verdict. The deferred unlock runs. Execute's recovery sees no panic, so there is one retained failure and no fallback charge or return to the worker. A later successful call can acquire the lock and account. F21 concerns termination earlier, in the request or classifier, where only admission was counted. [Execute defer](../gobreaker.go#L234) · [Reporting lock and trip hook](../gobreaker.go#L293) · [New probes](./_postprobe/identity_test.go)
- **N05.** In the configured Go 1.27.3 test runtime, the standalone control recovered nil from `panic(nil)`. At either the request or classifier seam, Execute therefore returned `(nil, nil)` with one admission, no outcome and no `ReadyToTrip` call. A panic with a typed-nil pointer in an interface recovered as a non-nil interface, counted one failure and rethrew that typed-nil value in both positions. The alternate runtime branch for the nil-interface input follows the same non-nil check and remains unexercised here. README's request-panic wording does not state the nil-recovery or reporting-panic limits.
